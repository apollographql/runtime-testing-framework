# Using a custom provider

This guide assumes you've completed the
["Creating a custom provider"](creating-a-custom-provider.md) guide. You should already have the
custom provider definition and script in your `rtf-hello-world` directory:

```bash
$ ls -R providers
providers
├── service-config.yaml
└── scripts
    └── generate-service-config.sh
```

## Declaring custom providers

Before we can use a custom provider in our test plan, we need to declare it. Custom provider
declarations tell RTF where to find the custom provider definitions and what names to use for them.

Let's update our `test-plan.yaml` to declare the custom provider. Add a `custom_providers` section
at the top level:

```yaml
name: Hello World
description: A test plan created as a guide for writing test plans
variables:
  scenario_variable: "scenario executed with test plan variable"
# --- Add custom provider declaration ---
custom_providers:
  - kind: local
    relative_path: providers
    using:
      service-config: service-config.yaml
# --------------------------------------
scenario:
  from:
    kind: local
    relative_path: configs/scenario.yaml
environment:
  from:
    kind: local
    relative_path: configs/environment.yaml
  overrides:
    setup:
      command:
        name: setup.sh
        kind: relative_path
        path: scripts/setup.sh
      file_providers:
        - name: config.txt
          env_var: CONFIG
          kind: inline
          content: |
            Config
```

The `custom_providers` declaration:

- **`kind: local`**: Specifies we're loading from a local directory
- **`relative_path: providers`**: The path to the directory containing custom provider definitions
  (relative to the test plan file)
- **`using`**: A map that associates a provider name (used in `type` fields) with the definition
  file
  - `service-config` is the name we'll use when referencing this provider
  - `service-config.yaml` is the definition file

> **Note** Custom providers can also be declared at the scenario or environment level, but declaring
> them at the test plan level makes them available to the entire test plan.

## Using custom providers with arguments

Now that we've declared the custom provider, we can use it in `file_providers` sections. Let's add
it to our environment setup so the service configuration files are available when we start the
environment.

Update the `environment.yaml` file to use the custom provider:

```yaml
name: Inline environment config
description: An inline environment config
setup:
  command:
    name: setup.sh
    kind: inline
    content: |
      #!/usr/bin/env sh

      PROCESS_ID="1"
      echo "Environment setup complete. PROCESS_ID=$PROCESS_ID"
      echo "{ \"process_id\": \"$PROCESS_ID\" }" > "$RTF_OUTPUT"
# --- Add custom provider to file_providers ---
  file_providers:
    - name: service-config
      env_var: SERVICE_CONFIG_DIR
      kind: custom_provider
      type: service-config
      service_name: "my-service"
      port: "3000"
      host: "0.0.0.0"
# ---------------------------------------------
  provides:
    - name: process_id
      description: The id of the process started in the environment setup
teardown:
  command:
    name: teardown.sh
    kind: inline
    content: |
      #!/usr/bin/env sh

      echo "Environment teardown complete. PROCESS_ID=$PROCESS_ID"
  env_vars:
    PROCESS_ID: "{{ process_id }}"
```

When using a custom provider:

- **`name`**: The name for this file provider instance (used in output)
- **`env_var`**: The environment variable that will contain the path to the generated files
- **`kind: custom_provider`**: Specifies we're using a custom provider
- **`type: service-config`**: Matches the name in the `using` map of our declaration
- **`service_name`, `port`, and `host`**: Arguments passed to the custom provider (must match the
  variable definitions)

> **Note** The `env_var` will point to a directory containing all files generated by the custom
> provider, not a single file. In our case, it will contain both `service.config` and
> `start-service.sh`.

## Verifying the output

Let's verify that our custom provider works correctly. First, let's check that the test plan
templates correctly:

```bash
$ rtf template test-plan.yaml --check --var process_id="dummy"
```

You should see the templated test plan without errors. Now let's run the test plan:

```bash
$ rm -rf output
$ rtf run test-plan.yaml
```

After running, let's check what files were generated:

```bash
$ ls -R output/providers
output/providers
service-config
  service.config
  start-service.sh
  ...
```

The `service-config` directory contains the files generated by our custom provider. Let's examine
them:

```bash
$ cat output/providers/service-config/service.config
SERVICE_NAME=my-service
PORT=3000
HOST=0.0.0.0

$ cat output/providers/service-config/start-service.sh
#!/usr/bin/env sh

# This script depends on service.config being in the same directory
CONFIG_FILE="$(dirname "$0")/service.config"

if [ ! -f "$CONFIG_FILE" ]; then
  echo "Error: service.config not found at $CONFIG_FILE"
  exit 1
fi

# Read the configuration file
. "$CONFIG_FILE"

# Dummy script that just echoes the service configuration
echo "Service: $SERVICE_NAME"
echo "Host: $HOST"
echo "Port: $PORT"
echo "Starting service $SERVICE_NAME on $HOST:$PORT"
```

Perfect! Both files were generated with the arguments we provided:

- The `service.config` uses `my-service` for the service name, `3000` for the port, and `0.0.0.0`
  for the host
- Both files reference the same variables
- The startup script depends on the config file and uses the same variables

## Using the generated files

The `SERVICE_CONFIG_DIR` environment variable will be available to commands in the environment
setup, scenario, and teardown. For example, we could update our setup script to use the generated
files:

```yaml
setup:
  command:
    name: setup.sh
    kind: inline
    content: |
      #!/usr/bin/env sh

      # Use the generated service configuration files
      if [ -f "$SERVICE_CONFIG_DIR/service.config" ]; then
        echo "Service configuration available at $SERVICE_CONFIG_DIR"
        # Could start the service here using the generated files
      fi

      PROCESS_ID="1"
      echo "Environment setup complete. PROCESS_ID=$PROCESS_ID"
      echo "{ \"process_id\": \"$PROCESS_ID\" }" > "$RTF_OUTPUT"
```

## Why custom providers are useful

Custom providers enable you to:

- **Encapsulate complex file generation logic**: The service configuration generation logic is now
  reusable
- **Share providers across test plans**: The same custom provider can be used in multiple test plans
- **Generate multiple interdependent files**: As we saw, both files reference the same variables and
  depend on each other
- **Parameterize file generation**: Different test plans can use the same provider with different
  arguments
